# 正式版架构

黑客松版本已经结束，这份文档记录正式版的需求，以及依据需求做的技术选型和必须遵守的规矩。需求变了，后面的选型和规矩要跟着改。

## 0. 需求

### 平台

1. **同一套代码发布到四个平台**：网页、Steam（Windows 和 macOS）、iOS（App Store）、Android（Google Play）。
2. **不考虑国内平台**：微信小游戏、蒸汽平台（Steam 国区）、国内安卓应用市场、App Store 国区都不在范围内。不为它们预留适配层，也不做相关的合规准备（版号、备案、国内服务器）。

### 屏幕

3. **手机小屏和电脑大屏是并列的一等公民**，从第一天起就按两档分别设计版式和交互，不是做完桌面版再缩放到手机上。黑客松版本把 1672×941 的桌面版式整体缩放到手机上，这条路不再走。

### 性能

4. **动画要极致丝滑**。性能基线定为三台设备，在它们上面全程不掉帧：
   - 2018 年的中端安卓手机；
   - iPhone 11；
   - 2020 年没有独立显卡的轻薄笔记本，外接 4K 显示器。

### 一致性

5. **各浏览器上的游戏内容几乎一样**。画面、动画、字体在 Chrome、Safari、Firefox、Edge 上应当几乎一致，不允许在某个浏览器上悄悄降级效果或改变玩法。

### 联机

6. **服务器权威，防止作弊**。规则只在服务端跑，客户端只发指令、只收事件，不跑规则、不持有完整局面。对手手牌、牌库顺序、题目答案这类隐藏信息不下发给客户端，每一方只拿到自己那份裁剪视图。黑客松版本"房主客户端跑规则、双方共享完整局面"的模式废弃。

## 1. 技术选型

| 层 | 选择 | 说明 |
|---|---|---|
| 游戏画面 | PixiJS v8（WebGL） | 对局、牌组编辑、开包、主页等一切带卡牌或大动画的界面 |
| 画布外界面 | React | 只做文字型界面，边界见第 2 节 |
| 动画 | GSAP | 补间 Pixi 对象的属性，Flip 插件不再使用 |
| 规则引擎 | 现有的 `packages/core`（TypeScript） | 保持纯函数、确定性、指令进事件出。联机时在服务端跑，单机在本地跑 |
| 联机服务端 | Cloudflare Worker + Durable Object | 一个房间一个 Durable Object，在里面跑 core、存对局状态、给每方算裁剪视图 |
| 网页 | 直接部署 | |
| Steam | Electron + steamworks.js | 自带 Chromium，Steam 上只有一种渲染引擎 |
| iOS / Android | Capacitor | 套系统 WebView 跑同一份网页构建 |

**为什么不是别的：**

- 不继续用 DOM：需求第 4、5 条（三台基线设备不掉帧、各浏览器一致）正是 DOM 方案做不到的。DOM 的排版、绘制、滤镜、CSS 3D 各家浏览器行为和代价都不同，且无法控制每帧成本。
- 不用 Cocos：它的决定性优势是官方小游戏适配，需求第 2 条已排除国内平台。原生手机渲染的优势对几十张卡的游戏用不上，代价却是放弃 React 工程体系并押注刚开源的 Cocos 4。
- 不用 Godot / Unity：网页导出在 iOS Safari 上不可靠或包体过大，满足不了需求第 1 条。

**Capacitor 是最弱的一环。** iPhone 11 没有问题；2018 年中端安卓走 Chrome WebView 余量最小。

## 2. React 与画布的边界

当年第一版 Pixi 方案失败的根因是卡牌在 DOM 和画布之间来回穿越，两套坐标系要手工交接。这次的规矩：

1. **卡牌绝不进 DOM。** 任何出现卡牌的界面整个放在画布上。
2. **带大动画的界面整个放在画布上**：对局、牌组编辑、开包、主页。
3. **React 只做文字型界面**：设置、商店、账号、弹窗、列表。这些界面自己做响应式，不依赖画布。
4. **画布和 React 之间只传数据，不传坐标。** 需要 DOM 元素和画布对象对位的设计一律不做。
5. **平台能力走一个接口层**：网络、音频、存储、图片加载、全屏、安全区、触感。场景代码不直接碰浏览器对象，方便按平台换实现。这七项每个壳都有、只是实现不同；壳独有的能力另算，写成接口上**可选**的一项（现在只有 Steam 那一项，迁移第 35 条）。

## 3. 性能纪律

针对需求第 4 条的三台基线设备。这些是硬性规矩，进代码评审清单。

1. **移动端每个元素不挂 Filter。** Pixi 的 Filter 每个都要一次离屏渲染，五六十个元素就是五六十次。手绘线条这类效果写进精灵自己的着色器，或者构建期烤进纹理。
2. **全屏半透明层同屏不超过三层。** 压暗层、发光、结算遮罩都算。无独显笔记本在 4K 下最先耗尽的是填充率。
3. **渲染分辨率封顶。** 设备像素比最高按 1.5 渲染，4K 屏不按 2 倍。低端档可以降到 0.75。
4. **卡面走图集加压缩纹理（KTX2），按场景装卸。** 不在界面上用原画，不让纹理常驻超过当前场景所需。
5. **文字只创建一次并缓存。** 卡面文字是静态的，一帧里不改文字内容。
6. **没有动画时停掉帧循环。** 省电、省热，也是验证"没有东西在偷偷动"的手段。
7. **效果分三档。** 首次启动跑一个小型 GPU 跑分定档，档位决定分辨率上限、特效开关和粒子数量。玩家可手动改。
8. **Pixi 显式指定 WebGL 路径，暂不开 WebGPU。** 驱动成熟度还不够，两年后再评估。
9. **每帧绘制调用不超过 200。** 超了先查合批是否被打断（纹理切换、混合模式切换）。
10. **动画只改 transform、alpha、tint 这类不触发重建的属性。** 不在补间里改文字、改纹理尺寸、改遮罩。

## 4. 一致性纪律

针对需求第 5 条。

1. **字体自托管并子集化**，不用 Google Fonts。文字在 canvas 上光栅化一次再上纹理，各浏览器结果几乎一致。
2. **只用 Pixi 内置着色器和自己写的中精度安全的着色器**，不用高精度浮点和依赖扩展的特性。
3. **处理 WebGL 上下文丢失。** iOS Safari 在内存紧张或切后台时会丢上下文，所有纹理走 Pixi 的资源管理，能自动重传。
4. **不允许按浏览器降级效果或改玩法。** 效果分档只按 GPU 能力，不按浏览器品牌。

## 5. 联机服务端

对应需求第 6 条。留在 Cloudflare Worker 加 Durable Object 上，不引入 Colyseus 一类的联机框架：它们的核心价值是状态增量同步，而 core 是指令进事件出，客户端靠事件流播动画，用不上；剩下的匹配和重连在 Durable Object 上各是几十行，换框架却要多一套常驻进程和运维。

1. **core 加两个纯函数**：`viewFor(state, player)` 算裁剪视图，`filterEvent(event, player)` 决定一条事件对某一方能看到多少。隐藏信息（牌库顺序、对手手牌、题目答案）只在这两处过滤，和引擎一样用 vitest 测。
2. **房间对象跑规则**。收到指令先核对座位身份，调 `execute`，新状态写进对象自带的 SQLite，再按玩家分别下发过滤后的事件。重连时下发裁剪视图快照。
3. **答题 autopilot 搬进服务端**，延时用 Durable Object 的 alarm。密钥在服务端，将来可以实时调模型。
4. **大厅对象做匹配**：全局队列，配对成功即创建房间并把房间码发给双方。房间码私人开房保留。
5. **握手验证身份**：WebSocket 升级请求带 JWT。账号用 better-auth 配 Cloudflare D1，Steam 端用会话票据换 JWT。
6. **客户端只留两个 driver**：`localDriver`（单机）和 `serverDriver`（联机）。host 和 guest 删除。

## 6. 测试与 CI

现状：仓库里有 6610 行测试，CI 一行都不跑。第一步不是写新测试，是把 typecheck 和 test 接进流水线。

两个原则：

- **确定性优先。** core 纯函数、假时钟、定种子，让绝大多数测试没有随机失败。一条不稳定的测试会让整条流水线失去信任。
- **每条纪律对应一条机器检查。** 第 2 节的边界靠依赖规则，第 3 节的性能靠计数器，第 4 节的一致性靠截图比对，需求第 6 条的防作弊靠隐藏信息测试。写不成检查的纪律迟早被打破。

### 6.1 流水线分两档

| 档 | 触发 | 时限 | 内容 |
|---|---|---|---|
| 快 | 每个 PR | 每个并行 job 10 分钟 | 6.2 到 6.8（含 6.6 的交互回归和剧本关键帧截图），Chromium 单浏览器截图 |
| 慢 | 合并到 main | 每个并行 job 20 分钟 | 6.9 的确定性指标、6.10 三浏览器一致性、6.11 端到端与四端构建，然后部署 |

「10 分钟」的口径是**每个并行 job 各自 10 分钟**，不是整条流水线。快档拆成四个互不依赖的
job 并排跑（`.github/workflows/ci.yml`）：`check`（类型 / lint / 设计令牌 / 单元测试，不开浏览器）、
`catalog`（组件目录页截图回归）、`scene`（对局场景的交互回归）、`keyframes`（剧本关键帧截图，
按剧本段再拆成四格）。
串成一条的话，光目录页那一步就要 6.8 分钟，整条已经到 8 分 56 秒，再加任何一条检查都顶破。
后两个一开始是同一个 job，两核跑机上放不下——关键帧是快档里最重的一步（桌面档一帧
2880×1620 的软件光栅，一条要三四分钟），所以每段剧本只停一帧，而且一格一台跑机。

**6.9 的确定性指标从快档挪到了慢档**：迁移第 18 条接上真对局场景之后，整批实测 17 分钟、
最慢一条 12.9 分钟（M2 无头软件渲染），两核的 ubuntu 跑机只会更慢，10 分钟的快档装不下。
它在慢档里按「视口 × 剧本」拆成八个并行 job，外加一个 `guard`（桩场景和泄漏那两条，
它们不按视口 × 剧本分格）（`.github/workflows/slow.yml`）。
6.9 的**时间指标**两档都不进：它机器相关、只出数不设门禁，而 GitHub 跑机没有 GPU，
量出来没有参考价值——那一组只在开发者本机跑（怎么跑见 `packages/bench/README.md`）。

### 6.2 静态检查

- tsc 严格模式、Biome 或 ESLint。
- 依赖边界：core 不 import 浏览器或 Node 对象，Pixi 场景不 import DOM，React 不 import 场景内部，包之间按 7.2 的方向单向依赖。用 dependency-cruiser 或 no-restricted-imports 做成规则，这是守住第 2 节和第 7 节边界的唯一机械手段。
- 循环依赖、未使用导出、单文件行数上限。

### 6.3 core 规则引擎

- 现有单元测试。
- 属性测试（fast-check）：随机合法指令序列打几千局，断言不变量：费用不为负、手牌不超上限、非法指令不改状态、同 seed 结果一致、状态 JSON 往返后相等。
- 隐藏信息测试：任意状态下 `viewFor` 的输出不含对手手牌、牌库顺序、题目答案，`filterEvent` 不泄露。作弊防线就靠这两条。
- 内容覆盖：每张已启用的牌和每位已启用的英雄至少被一个测试点名，没有的挂。
- 回放测试：真实对局录成指令序列当 golden，引擎改动后回放，事件流不一致要人工确认。

### 6.4 内容数据

- zod 校验 schema。
- 资源引用存在，推广现有 assetManifest 测试到全部内容。
- 预生成答案表完整：每题、每卡、每变体都有值。
- 注入提示词和预生成脚本引用同一来源。
- 文案 key 各语言齐全。

### 6.5 演出编排层

- 假时钟喂事件流，输出的演出指令序列做快照比对。
- 每种事件类型要么有演出，要么显式声明忽略，漏掉的挂。

### 6.6 Pixi 场景

- 截图回归：Playwright 无头浏览器，固定步进时钟，剧本关键帧和 golden 用 pixelmatch 比。因为确定性，容差可以很小。
  落成两处：**静止**的版式在组件目录页（`packages/client/dev/storybook`，每个条目一张，
  含对局场景和构筑页两档版式各三个关键帧），**演出途中**的几拍在
  `packages/bench/tests/keyframes.spec.ts`（四段剧本各停一帧）。两边的容差同口径，
  基线都按平台分目录（字体光栅化在 macOS 和 Linux 上对不齐）。
  目录页那条按条目**分片跑**（`catalog.spec.ts` 的 `SHARDS`），CI 快档一片一个并行 job——
  整页一条用例已经顶到快档 10 分钟的口径了。
- 交互测试：合成指针事件模拟拖拽出牌、点选目标，断言场景发出的指令。
  也落成两处：纯逻辑那半在 `packages/canvas/test/` 下的 `duelInput` / `duelTargeting` /
  `duelHeroSkill` / `deckInput` 四个文件（vitest，组件用替身，管「判定对不对」），真浏览器那半在
  `packages/bench/tests/interaction.spec.ts`（真 DOM 指针事件、真命中测试，管「点不点得到」）。
  只有后者能发现「选目标层把候选的点击全吃了」这一类问题。
  构筑页那一套（从卡池拖进牌组、拖出去移除、点加号、三种加不进去的理由）在 `deckInput.test.ts`。

### 6.7 服务端

- 用 Cloudflare 官方的 vitest-pool-workers 在 workerd 里直接测 Durable Object，含 SQLite 和 alarm。
- 作弊测试：用对方座位发指令、发非法指令、伪造 JWT、断线后冒充重连，全部要被拒。
- 两个 WebSocket 客户端打完整局，现有 371 行 smoke 脚本改造进 vitest。

### 6.8 React 界面与包体

- Testing Library 组件测试，只测逻辑分支，不测样式。
- 组件目录页（7.1）每个条目截一张图做回归，样式改动在这里暴露。
- size-limit 卡首屏 JS 和每场景资源。第 31 条先接上了 `ui` 这一个包
  （配置和「上限为什么是这个数」在 `packages/ui/.size-limit.js`，`pnpm size` 跑它，
  进了快档的 check job）。首屏 JS 和各场景的资源要等壳那边真打出产物才量得了。

### 6.9 性能

需求第 4 条的三台基线设备是目标，但 CI 里不靠"在某台机器上跑到多少帧"来把关，因为 CI 机器和基线设备不是同一种硬件。性能拆成两类指标：**确定性指标**机器无关，用硬上限断言；**时间指标**机器相关，只和 main 分支做相对比较。不做真机验收。

**前提：脚本化性能场景。** 所有指标都建立在一个确定性的剧本上，没有它，所有数字都是噪声。

- 做成正式的包 `packages/bench`，不是临时脚本。
- 剧本固定：开局发牌、连续出牌十次、放大查看、一轮结算、牌组编辑滚动、开包。每段可单独跑（开包那段等对应场景写出来）。
  「牌组编辑滚动」量的是构筑页那一屏整批换掉的开销（迁移第 28 条）：**正式版的卡池是翻页不是滚动**
  （画布上做滚动要一层遮罩加离屏剔除），名字沿用 6.9 表原来的叫法。它每一下动作之间按**真人的节奏**
  等（0.75 秒），不是「够画面重排完就行」——那条「稳态每帧堆分配」是拿总分配除以动作帧数算的，
  剧本压得太短量到的全是一次性开销。
- 时钟固定步进：GSAP 和 Pixi 的 ticker 由测试手动推进，不用真实时间。
- 随机定种子，资源集合固定，效果档位显式指定。
- 同一段剧本在任何机器上产生的确定性指标必须一模一样，这本身就是一条断言。

**确定性指标：硬上限，慢档。** 在普通跑机上跑（本来定在快档，跑起来装不下，理由见 6.1）。数字通过包一层 WebGL 上下文计数、Pixi 的渲染统计和自己封装里的计数器得到。

| 指标 | 怎么测 | 上限 | 对应纪律 |
|---|---|---|---|
| 每帧绘制调用数 | 数 drawElements / drawArrays | 每帧不超过 200 | 3.9 |
| 合批被打断次数 | 数纹理绑定、着色器切换、混合模式切换 | 每帧桌面档不超过 132，手机档不超过 108 | 3.9 |
| 离屏渲染次数 | 数 framebuffer 绑定 | 两档都是 0 | 3.1 |
| 过度绘制倍数 | 调试模式用叠加混合画一遍再读回平均值 | 不超过 3 倍视口 | 3.2 |
| 动画期间纹理上传次数 | 数 texImage2D | 0 | 3.4 |
| 常驻纹理内存 | 累加已上传纹理尺寸 | 对局场景不超过 48 MiB | 3.4 |
| 运行期着色器编译 | 数 compileShader | 预热后为 0 | |
| 同步阻塞调用 | 数 readPixels、getError、getParameter | 动画期间为 0 | |
| 动画期间文字对象重建 | 文字封装里计数 | 0 | 3.5 |
| 稳态每帧堆分配 | DevTools 协议采样堆分析 | 每帧不超过 2 KiB | 3.10 |
| 空闲时帧循环 | 剧本结束后数 ticker 回调 | 0 | 3.6 |
| 泄漏 | 连打十局后强制 GC | 堆和纹理内存回到基线，偏差不超过 5% | |

**时间指标：相对回归，只在本机跑。** 要 GPU 才有意义，而 GitHub 的 Linux 跑机是软件渲染，
所以仓库里不加这一条的工作流，由开发者在本机跑并和 main 比（`packages/bench/README.md`）。

- 指标：帧时间 p50、p95、p99；超过预算两倍的卡顿帧数量；GPU 每帧耗时（WebGL disjoint timer query）；主线程脚本时间。
- 帧时间从 Chrome 的 trace 里取，用 Perfetto 的 trace_processor 提取，不在页面里自己计时。
- 主线程指标在 DevTools 协议四到六倍 CPU 节流下测，近似 2018 年中端安卓的 CPU。它不节流 GPU，所以只约束 JS 一侧。
- 每次跑五遍取中位数抗噪声。和 main 分支的记录比，任一指标退步超过 10% 就挂。
- 绝对值不作为门禁。

第 18 条那次是整套对局界面（顶栏、侧栏两块面板、Token 细条、战场两排、手牌、对手手牌）

**第 20 条这一轮顺带修掉了结算层的两处**（都是加上「一轮结算」剧本才量出来的）：

## 7. 代码管理

黑客松的 hack 模式到此为止：一个文件几千行、样式堆在一个全局 css 里、同样的按钮和边框每个界面重画一遍，正式版不再允许。

### 7.1 统一的 UI 组件库

1. **只有两套组件库，各自唯一。** 画布上的 Pixi 组件（卡牌、按钮、边框、面板、气泡、数字跳动）在 `canvas`，画布外的 React 组件（按钮、边框、列表、弹窗、表单）在 `ui`。每种组件只有编号的变体：按钮 A、B、C，边框 X、Y、Z。界面代码只能选变体、传数据，不能自己画。
2. **能复用绝不重写。** 新界面需要新样式，先给组件库加变体，再在界面里用。界面里手写同类东西，代码审查不通过。
3. **组件目录页。** 一个开发专用页面列出所有组件、全部变体、全部状态（普通、悬停、按下、禁用、加载）。React 部分用 Storybook，Pixi 组件在同一目录页里嵌画布展示。每个组件必须有目录页条目，没有条目视同没写完。6.6 和 6.8 的截图回归直接拿目录页当输入。
4. **设计令牌只定义一次。** 颜色、字号、间距、圆角、动效时长放在 `design` 包，Pixi 和 React 共用，禁止在组件里写死数值。

### 7.2 项目结构

```
packages/
  core/       规则引擎，纯函数，不带数据
  content/    卡牌、英雄、题目等数据和 zod schema
  protocol/   客户端与服务端之间的消息类型
  design/     设计令牌
  platform/   平台能力接口，以及 web、electron、capacitor 三个实现
  canvas/     Pixi 组件库、各场景、演出编排
  ui/         React 组件库
  client/     装配层：路由、屏幕、状态、本地驱动和服务端驱动
  server/     Worker 与 Durable Object
  bench/      6.9 的性能剧本
apps/
  web/ steam/ mobile/   三个壳，只有入口和构建配置，不写业务
```

规矩：

1. **依赖单向。** `core` 不依赖任何包；`content`、`protocol` 只依赖 `core`；`canvas` 依赖 `core`（演出编排层要读事件和视图的类型）、`design`、`platform`，`ui` 依赖 `design`、`platform`，两者不依赖对方；`client` 装配一切；`server` 只依赖 `core`、`content`、`protocol`；`bench` 依赖 `canvas`、`design`、`platform`、`core`（6.9 的性能剧本要开一局脚本化对局）。方向写进 6.2 的依赖规则，违反就挂。
2. **跨包只走包入口。** 每个包一个 `index.ts`，内部文件不对外。
3. **单文件不超过 400 行**，lint 卡死，一个豁免都没有。写这份文档时旧客户端的 MatchStage 有 3950 行、DeckScreen 3115 行、styles.css 7515 行——那些是要拆掉的对象，不是要迁移的对象。
4. **样式跟着组件走。** React 组件各自带样式文件，不再有全局 css；Pixi 组件的样式来自设计令牌。
5. **开发专用页面放在 `client/dev`**，包括组件目录页和调试场景，生产构建剔除。
